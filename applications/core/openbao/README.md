## Why it exists in SaaS Fabric

OpenBao is the platform's secrets capability. SaaS Fabric needs somewhere to
hold and issue per-client credentials that is not Git and not a static
Kubernetes Secret, and every other platform component eventually sources its
credentials from it. It is core because the platform has no credible secret
story without it.

## Ownership boundary

Argo CD owns the OpenBao *deployment*. It does not own its contents.

| Resource | Owner |
|---|---|
| StatefulSet, storage, service, UI, RBAC | this repository |
| Initialisation and unsealing | **LucentRoot: this repository, automatically.** Production: an operator, with recovery material held externally |
| Kubernetes auth method for External Secrets | LucentRoot: established at first start. Production: a one-time step |
| Auth methods and policies for a client | client OpenTofu |
| Per-client namespace inside OpenBao | client OpenTofu |

## Lifecycle differs by environment, deliberately

This is the one part of OpenBao that is not shared, because the two environments
want opposite things from it.

| | LucentRoot | Production |
|---|---|---|
| Storage | disposable | durable |
| Seal | static key, generated in-cluster | Shamir today; an external key vault is the destination |
| Initialisation | automatic, at first start | deliberate |
| Recovery keys | none generated | required, held outside the cluster |
| Root token | revoked, never returned | captured and stored |
| After a rebuild | a new, empty instance | restored, never rebuilt |

Both are expressed as two values the environment supplies — `sealStanza` and
`initializeStanza` — which the chart composes into the server configuration. The
deployment itself stays shared.

### LucentRoot: nobody touches it

OpenBao initialises and unseals itself. Nobody runs `bao operator init` or
`bao operator unseal`, and nothing from a previous installation is needed to
build the next one.

```bash
kubectl -n secrets exec openbao-0 -- bao status   # Initialized: true, Sealed: false
```

Self-initialisation requires auto-unseal, generates **no recovery shares**, and
revokes the root token rather than returning it — so there is no key material
for anyone to capture or lose. The seal key it uses is generated by
[`../openbao-seal`](../openbao-seal/) and is disposable by design: after a
rebuild there is no prior data to decrypt.

At first start it establishes the `secret/` kv-v2 mount, the Kubernetes auth
method, a policy scoped to `secret/platform/*`, and the role bound to the
External Secrets service account. `secret/clients/*` stays unreachable from it.

It also establishes the human administrative path, because bootstrap surfaces no
root token: a `platform-admin` policy and an `operator` role bound to the
`openbao-operator` service account. An operator mints a short-lived token with
`kubectl create token` and exchanges it for an OpenBao token, so authority comes
from a Kubernetes identity rather than a stored password and no standing
credential exists to leak or rotate. Without it OpenBao would have exactly one
identity — External Secrets — and its UI would be reachable on the operator plane
and unusable by anyone. See
[`../operator-access`](../operator-access/overlays/lucentroot/).

**Destroying LucentRoot destroys its OpenBao state and its seal key together.**
That is intended, not a caveat.

### Upstream limitation: `initialize` runs once, and only once

Worth stating plainly, because it bounds what this design can do.

OpenBao executes the `initialize` stanza **only on first startup**, and this is
deliberate upstream behaviour rather than an oversight — it is what stops someone
who can edit the configuration from later granting themselves privileged access.
Upstream's remedy for applying a change is to *"remove all storage and
re-initialize from scratch"*, and it says the stanza
*"should not be treated as the long-term owner of these resources"*.

The consequence for this repository:

| | |
|---|---|
| Editing the stanza in Git | changes nothing on a running instance |
| Argo CD's report | `Synced` and `Healthy` — the *manifest* matches |
| Actual state inside OpenBao | whatever first startup established |

**Git and the running instance can therefore diverge silently, and Argo CD
cannot detect it**, because the drift is inside OpenBao's storage rather than in
a Kubernetes object. This is the one place in the platform where "reconciled by
Argo CD" does not mean "matches Git".

On LucentRoot the remedy is cheap and already the documented lifecycle: delete
the StatefulSet and both PVCs and let it rebuild. Its policies and auth methods
are effectively **immutable-by-rebuild**, which is acceptable precisely because
its storage is disposable.

It does not generalise to production, where storage must survive. Auth methods
and policies there belong in a tool that can reconcile them continuously — the
client layer already owns per-client policies through OpenTofu, and platform
policies should follow the same route rather than growing this stanza.

### Production: state that has to survive

Neither self-initialisation nor a disposable seal is correct where the data
matters. Production is initialised deliberately, with recovery material captured
and held outside the cluster, and a restarted pod is unsealed by an operator
until `saas-fabric-hosting` supplies a key vault to seal against.

No root token, unseal share or recovery key is permitted in this repository, in
either environment.

## How secrets reach workloads

OpenBao is the authority; it is not the delivery mechanism.
[External Secrets](../external-secrets/) reads it and materialises Kubernetes
Secrets, joined by a single [`ClusterSecretStore`](../secret-store/). A workload
puts its values at `secret/<name>` and declares an `ExternalSecret`; nothing
about those values enters this repository.

## Dependencies

None hard. Wave `10`, alongside the other foundations.

## Configuration owned by this repository

- StatefulSet topology (Raft, replica count per environment);
- data and audit volume sizing, storage class and retention policy;
- service, UI exposure and health probing;
- the seal configuration *reference* for auto-unseal.

## Configuration expected from outside this repository

- **Unseal / auto-unseal material** — a key vault key and an identity permitted
  to use it, created by `saas-fabric-hosting`.
- **Tailnet access**, if operators need the UI. Workloads reach OpenBao
  cluster-locally at `openbao.secrets.svc.cluster.local:8200` and need no
  ingress at all; LucentRoot additionally exposes it on the operator plane. It
  is never on the product edge. See
  [docs/architecture.md](../../../docs/architecture.md#exposure-planes).
- **Policies, auth backends and secret engines**, which are reconciled by the
  client layer per client.

## Resources unsafe to prune

The Raft data and audit PVCs are retained on scale-down and delete via
`persistentVolumeClaimRetentionPolicy: Retain`. Removing this Application from
Git deletes the StatefulSet but leaves those volumes behind by design; they must
be removed deliberately.
