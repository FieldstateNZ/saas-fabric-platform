# ApplicationSets

There are none, deliberately.

## Why not

An ApplicationSet would be the obvious way to avoid writing one `Application`
per component. It was not used because of ordering.

Argo CD sequences resources within a single Application by sync wave, and it has
a built-in health check for the `Application` kind: a child `Application` counts
as Healthy only when the application it names is Healthy. In an app-of-apps,
sync waves therefore give real dependency ordering — wave `10` does not begin
until wave `0` is genuinely running.

Applications generated by an ApplicationSet are created by the ApplicationSet
controller rather than by a parent's sync, so their sync waves do not order them
against each other. They all begin at once. Sequencing them requires progressive
syncs (`spec.strategy: RollingSync`), which is beta and behind a controller
feature flag.

The platform has hard ordering requirements:

```text
CloudNativePG operator + CRDs  →  Keycloak database Cluster  →  Keycloak
```

Depending on retry-until-it-works for that would be relying on accidental
reconciliation order, which is exactly what this platform declines to do.

## But what about the repetition?

There is none left to remove. The usual reason to reach for an ApplicationSet
here would be one Application per component *per environment*; instead a single
shared definition is bound to an environment by Kustomize replacements — see
[`environments/components/environment-config`](../../environments/components/environment-config/kustomization.yaml).

Adding a component is one `application.yaml` and one line in a kustomization.
An abstraction that removes that is not paying for itself.

## When to introduce one

When a set of Applications is genuinely generated rather than authored, and
nothing in the set has an ordering requirement against anything else. The
strongest candidate is the catalogue: once SaaS Fabric's capability model drives
which capabilities exist, catalogue Applications stop being authored and start
being derived, and a Git generator over
[`applications/catalogue`](../../applications/catalogue/) becomes the right
tool. Catalogue applications all sit in wave `40` and depend on nothing, so
losing wave ordering between them costs nothing.

Core applications should stay as they are.
